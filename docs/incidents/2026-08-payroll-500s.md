# Incident: intermittent 500s on payroll submit under the nightly accrual job

**Date:** 2026-08-30
**Status:** Diagnosed — fix pending (Phase 8 Task 4)
**Affected:** `POST /api/v1/payroll/runs/{id}/submit`, and (incidentally) `POST /actuator/payroll-accrual` itself
**Last leaky commit:** `1e5c659446ea787b05fb4376a0b8819ea8e119bc` — `git checkout 1e5c659` reproduces the broken state this document diagnoses (the leak itself landed in `6e9e055`; every commit through `1e5c659` leaves it unchanged). Task 4 fixes it after this SHA.

This is a diagnosis written from the observables in `docs/incidents/payroll-500s-evidence.md` and `docs/incidents/payroll-500s-samples/`, reasoned through as if the cause were not already known. No application code, Hikari setting, or Postgres setting is touched in this document — that is Task 4.

## 1. Symptom, as seen from outside

A caller with no knowledge of any batch job sees `POST /api/v1/payroll/runs/{id}/submit` behave normally — fast `200`s on success, fast `409`s on an already-submitted run — for the first several seconds of any given window, and then, with no warning, some fraction of calls start taking **exactly ~30 seconds** each before failing with a bare `500`:

```json
{"timestamp":"2026-08-30T21:23:17.032Z","status":500,"error":"Internal Server Error","path":"/api/v1/payroll/runs/51/submit"}
```

Two things about this symptom are load-bearing for the diagnosis before any internal instrumentation is even consulted:

- **The failing calls all take the same ~30 seconds**, not a spread of durations. That is not what a slow query or an overloaded server looks like (those degrade gradually, with a widening but continuous distribution); it is what a fixed client-side wait-then-give-up timeout looks like.
- **The failure does not go away when the load stops.** An isolated, single request sent 2m45s after the sustained traffic generator finished — no concurrent load, no other in-flight callers — still took 30.026321s and still 500'd. That single fact, on its own, rules out anything framed as "the server was momentarily overwhelmed": a transient spike self-heals once the load causing it stops; this did not, at any point checked, including nearly six minutes after the one action that could plausibly have caused it.

An on-call engineer with only these two observations already knows two things: something is handing out a fixed ~30-second wait before failing (a client-side pool timeout is the standard shape for that), and whatever broke it did not un-break itself — it's a standing condition, not an episode.

## 3. Hypotheses considered and ruled out

**Slow queries / lock contention.** If some query were simply slow, or blocked waiting on a row/table lock, `pg_stat_activity` would show one or more backends in state `active` for an extended period (a query genuinely running), or entries in `pg_locks` for a blocked statement. Every sample taken during the incident shows exactly `active | 1` (a single active backend — plausibly the diagnostic `psql` session or Postgres's own background activity, not 8+ stuck submit requests) and `idle | 10`. Separately, the application-side exception is `CannotCreateTransactionException: Could not open JPA EntityManager for transaction` — this is thrown *before* Hibernate issues any SQL on the failing request's own attempted connection; there is no query for it to be slow on. Ruled out.

**A stuck/uncommitted transaction.** A transaction that was opened and never committed or rolled back would show as Postgres state `idle in transaction`. Every sample, throughout the entire incident, shows zero such sessions (see §4). Ruled out — directly, not by inference.

**The submit endpoint itself being at fault.** Two observables argue against this. First, the failure occurs at connection acquisition, before `PayrollService.submit`'s own method body ever runs — the stack trace's outermost frame is Spring's transaction manager trying to open a connection, not any of `PayrollService`'s own logic. Second, and more tellingly: `POST /actuator/payroll-accrual` — a completely different endpoint, a different controller-equivalent, a different code path — fails with the *identical* symptom (`500`, ~30-32s, the same Hikari message) at 21:16:50.328. Two unrelated endpoints failing the same way at the same time points at something they share (the connection pool), not something specific to either one's own code. Ruled out.

**Postgres's own connection limit (`max_connections`) reached.** The total connection count visible in `pg_stat_activity` (`1 active + 10 idle` = 11, plus whatever background/system backends Postgres always carries) is nowhere near exhausting a default `max_connections` of 100 (confirmed unchanged from the test-suite incident's own finding, and nothing in this project's config touches it). More directly: a server-side connection-limit rejection surfaces as Postgres itself refusing the connection (historically `FATAL: sorry, too many clients already` or similar, propagated through the driver) — a fundamentally different failure than `HikariPool-1 - Connection is not available, request timed out after 30006ms`, which is Hikari reporting that *its own local pool*, not the server, has nothing to hand out. Every log line also reads `total=10` — the pool's own configured ceiling (HikariCP's default `maximum-pool-size`), not anything resembling Postgres's 100. Ruled out.

**Contrast: the test-suite pool-exhaustion incident.** Both incidents are colloquially "pool exhaustion" and both surface through a `HikariPool-1 - Connection is not available` message, but the parenthetical numbers describe opposite conditions:

| | Test-suite incident | This incident |
|---|---|---|
| Hikari's own reading | `total=0, active=0, idle=0, waiting=N` | `total=10, active=10, idle=0` |
| What that means | The pool has **no connections at all** — Hikari's live connections had silently died (the container underneath a cached Spring context had been swapped for a new one on a new port) and it could not open replacements against a target that no longer answered | The pool has its **full complement of 10 real, live connections** — confirmed independently via `pg_stat_activity` showing exactly 10 `idle` sessions against the *same, still-running* Postgres instance |
| Real-world shape | The server (or the path to it) is unreachable | The application is holding every connection it was given and never giving any back |

`total=0` names a pool that cannot *establish* connections; `total=10, active=10` names a pool that established all of them and never released any. Same symptom class, same log message shape, opposite root cause — which is exactly why the number inside the parentheses, not the message text, is the thing worth reading first.

## 4. The absent signal

Across all 19 pool-state samples and the standalone check afterward, this query:

```sql
SELECT pid, state, now() - state_change AS age, left(query,80) AS query
FROM pg_stat_activity WHERE datname='wmp' AND state='idle in transaction';
```

returned zero rows, every single time. That absence is itself the finding, not a gap in the evidence. It means: whatever last ran on each of the ten held connections *finished* — committed or ran to completion under autocommit — and the connection was simply never handed back afterward. Postgres has no way to see anything wrong with a plain `idle` session; from the database's point of view, ten quiescent, fully-committed connections sitting idle is indistinguishable from ten connections in a perfectly healthy pool waiting for their next request.

This rules out any remediation aimed at *stuck transactions specifically*. In particular, `idle_in_transaction_session_timeout` — a real Postgres setting, and the natural first instinct for "a connection is stuck" — terminates sessions that have been sitting idle *while a transaction is still open*. It would not have fired here, because at no point was any of these ten sessions ever in that state. The defect is not "a transaction got left open too long"; it is "a `java.sql.Connection` object is still referenced by application code and was never told to close," which produces a connection that looks, from Postgres's side, exactly like a healthy one doing nothing at the moment — because that is genuinely what it is doing. The problem is entirely on the application side of the socket; nothing observable in `pg_stat_activity`'s `state` column distinguishes "leaked" from "pooled and idle."

## 5. What pinned it to the accrual job

Two candidate observables from the ten leaked backends: their `last_query`, and the tight clustering of their ages (all opened within ~1.4 seconds of each other).

**Age clustering is consistent with, but does not by itself prove, a single batch process.** A burst of ordinary concurrent user traffic arriving in the same narrow window would produce similarly clustered connection ages. Clustering narrows the field; it doesn't name a culprit.

**`last_query` is what actually closes the case:**

```
last_query
INSERT INTO payroll_accruals (employee_id, period_start, per...
```

on all ten, identically. `pg_stat_activity.query` records the literal last statement each backend executed — this is not an inference from timing or behavior, it is Postgres reporting, per connection, exactly what SQL ran on it. `payroll_accruals` is written by exactly one code path in this codebase (`PayrollAccrualJob`'s upsert); nothing else in the application ever issues an `INSERT` against that table. Ten held connections, each independently reporting that the last thing they did was run this specific job's own SQL, is a direct statement of fact about those ten connections, not a correlation between two independently-observed events. That is why this observable is conclusive rather than merely suggestive.

**Is this evidence sufficient, or would a real incident want more?** For closing the case as stated, it's sufficient — the SQL text alone is unambiguous because only one code path in the entire application produces it. But a real (non-portfolio) investigation would still want two things this evidence doesn't provide: first, a **leak-detection stack trace** naming the exact line of code that opened each connection — `last_query` tells you *what ran*, not *what code opened the connection and failed to close it*; Hikari's own `leakDetectionThreshold` (not configured in this run — that's Task 4) exists specifically to log that stack trace, and would have been more directly conclusive than inferring from SQL text. Second, an **independent correlation** between the accrual run's own employee count and the number of connections leaked (this run's evidence does not capture how many employees `PayrollAccrualJob` processed on this particular invocation, so that specific cross-check — "N employees processed × 1-in-5 leak rate ≈ 10 leaked connections" — is not something this evidence set can verify; noting that it wasn't captured here rather than asserting a number that isn't in the data).

## 6. Reconciling the numbers

**119 raw log occurrences vs. 59 actual failed requests.** Grepping the raw log for the literal string `HikariPool-1 - Connection is not available` returns 119 matches, but each *failed request* produces the message twice under ordinary circumstances: once as a `WARN` line from Hibernate's own JDBC error logging, and once more embedded in the root-cause exception's own message line further down in the same logged stack trace (`java.sql.SQLTransientConnectionException: HikariPool-1 - ...`). Counting each type separately: **59 WARN lines, 59 root-cause exception lines** — 118, one short of 119. The 119th comes from the one request that failed via a different exception wrapper (`DataAccessResourceFailureException: Unable to acquire JDBC Connection [HikariPool-1 - ...] [n/a]`, rather than the more common `CannotCreateTransactionException`) — that wrapper's own summary message embeds the text a third time, for that one request only. `58` `CannotCreateTransactionException` occurrences + `1` `DataAccessResourceFailureException` occurrence = `59` distinct failed requests, matching the WARN-line count exactly. This reconciles cleanly: **119 = 59 failed requests × 2 (WARN + root-cause line), + 1 extra from the one request whose wrapper exception happens to repeat the message a third time.**

Of those 59 failed requests: 56 are recorded in `submit_traffic.csv` (the systematic load-generator traffic), and 2 are the manual follow-up probes in §2's timeline (the isolated recovery check and the response-body capture) — `56 + 2 = 58`, matching the 58 `CannotCreateTransactionException` occurrences exactly. That leaves the one `DataAccessResourceFailureException` occurrence, timestamped `21:16:50.282` — 46ms before the accrual trigger's own HTTP call returned its `500` at `21:16:50.328`. The timing lines up closely enough to be the accrual trigger's own request, most plausibly failing inside the job's *own* per-employee JPA read (a repository call carries a different implicit transaction boundary than `PayrollService.submit`'s explicit one, which would explain the different exception wrapper) rather than one of `PayrollService.submit`'s calls — but this is an inference from timing and exception shape, not something the log directly labels by endpoint or thread purpose, so it's presented as the best-supported reading of this one line, not a certainty.

**The `hikaricp.connections.timeout` counter** reached `57.0` by the last sample taken before the sampling window closed (21:20:39.043, per `evidence_samples.txt`) — consistent with the 56 load-generator failures plus the 1 accrual-trigger failure, all of which had occurred by then. It is not, on its own, checkable against 59, because the two manual follow-up probes happened *after* sampling had already stopped; evidence.md records the counter read `58.0` after the first follow-up probe, but the metric was never re-queried after the second one, so a value of `59` at that point is expected but **not captured** — stating that rather than assuming it.

**Arithmetic check: is 56 consistent with 8 workers under continuous 30-second-timeout saturation?** Using the load generator's own recorded span for its 500s — first at 21:16:20.041 (request start; see the correction below), last completing around 21:19:52.103 (start 21:19:22.080 + its own 30.023s) — gives a saturated window of **≈182.0 seconds**. Under perfectly synchronized saturation, each of the 8 workers can complete `floor(182.0 / 30) = 6` full 30-second block-then-fail cycles in that span (using 180 of the 182 seconds), for `8 × 6 = 48` expected failures. The observed count is 56 — about 8 more than this idealized estimate, same order of magnitude, not a wild mismatch, but not an exact match either. The gap is plausibly explained by the pool not becoming exhausted at one synchronized instant across all 8 workers — the leak accumulates one connection at a time as the accrual job works through employees, not as an instantaneous cliff, so different workers' own request-in-flight-at-the-moment-of-exhaustion could start their own first blocked cycle at slightly different offsets, letting some of them fit in an extra completion within the same wall-clock window. The evidence does not let this be pinned down further: the load generator did not log a per-worker identifier, so individual workers' cycle counts cannot be reconstructed from `submit_traffic.csv` as captured. Stating this rather than forcing the arithmetic to land exactly on 56.

*Correction to a reading in the evidence file:* `docs/incidents/payroll-500s-evidence.md` flagged its first `500` row's timing as possibly anomalous, reasoning `ts − elapsed` and getting a start time ~28 seconds before the trigger was even sent. That reasoning inverted the arithmetic — the worker logs `ts` *before* issuing the request, so the request's own start time is `ts` itself, and it *completes* at `ts + elapsed`, not `ts − elapsed`. Recomputed correctly: `ts=21:16:20.041`, `elapsed=30.083122s` → the request completed at **21:16:50.124**, which lands within 124ms of the application log's own first occurrence (21:16:50.248) — the two independent sources agree. There is no timing anomaly; the evidence file's flagged caveat does not hold up under the corrected arithmetic.

**What the 200/409/500 mix says about when the pool actually crossed over.** All 28 successful transitions land within the first 5.017 seconds of the test (21:15:40.101–21:15:44.676) — entirely before the accrual trigger is even sent (21:16:17.776), roughly 33 seconds earlier. That crossover (200s stopping, 409s starting) has nothing to do with the leak: it simply reflects that 8 racing workers exhaust a pool of only 28-29 distinct submittable runs almost immediately, after which every further attempt against an already-submitted run correctly 409s — this is the test's own design, not a symptom. The *meaningful* crossover is 409s giving way to 500s, which begins at ~21:16:20.04 — about **2.265 seconds** after the trigger was sent (21:16:17.776). That gap says the accrual job leaks enough connections to fully exhaust a 10-connection pool (given the job's own `1-in-5` leak rate, that means processing at least its first 50 employees) in about two and a quarter seconds — fast, and consistent with cheap, sub-50ms-per-employee database work against a small local dataset.

## 7. Root cause

`PayrollAccrualJob` opens a raw `java.sql.Connection` via `DataSource.getConnection()` for every 5th employee it processes and, on that path only, never closes it — no `try`-with-resources, no `finally` — so the connection (and the `PreparedStatement` opened on it) is never returned to HikariCP's pool; HikariCP has no mechanism that reclaims a connection the application still holds a live reference to (that is specifically what an enabled `leakDetectionThreshold` would only *report*, not what any currently-active setting *prevents* or *recovers* from), so each full run of the job permanently removes connections from the pool's usable capacity, two for every ten employees processed, until — within roughly two seconds against this dataset — the entire default 10-connection pool is consumed; every other caller needing a database connection, including the completely unrelated payroll-submit endpoint, then blocks for the full 30-second `connection-timeout` before failing with `SQLTransientConnectionException`, and the pool never recovers on its own because nothing ever closes the leaked connections short of restarting the process.

## Fix

**The leak itself.** `PayrollAccrualJob`'s upsert now acquires its connection and prepared statement with try-with-resources, unconditionally, for every employee — the branch that routed every 5th employee down a path with no resource management is gone, along with the `// INTENTIONAL LEAK` marker. Same accrual computation, same writes, same `INSERT ... ON CONFLICT DO UPDATE` upsert — only the connection handling changed.

**Bounding the pool (main profile, `application.yml`):**

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 10
      connection-timeout: 5000
      leak-detection-threshold: 2000
```

- **`maximum-pool-size: 10`** — unchanged from Hikari's own default, but now explicit rather than implicit. Nothing in this project's own evidence argues for a bigger number: every load measurement taken across Phases 6-7 (`docs/measurements.md`) served real request volume comfortably within a 10-connection pool, and a bigger pool would only mean more connections available to leak before exhaustion — worse blast radius, not better. Keeping it at the already-proven-adequate value, explicit rather than defaulted, is the honest choice here.
- **`connection-timeout: 5000`** (5s, down from Hikari's 30s default) — every measured p95 latency for this application's real endpoints, across every phase of `docs/measurements.md`, stayed under 100ms, even at depth, even without an index. A caller legitimately waiting anywhere close to even 1 second for a connection already indicates something is wrong; 5 seconds is a generous margin above that while still failing five to six times faster than the 30-second wait this incident's callers actually experienced. This does not fix anything — it only changes how long a caller waits before finding out something is broken.
- **`leak-detection-threshold: 2000`** (2s) — new. This is the one addition that actually shortens time-to-detection rather than just blast radius. **Its relationship to `connection-timeout` matters and was chosen deliberately**: `leak-detection-threshold` is a per-connection "how long has this one been checked out" clock that logs a `WARN` (with the stack trace of whoever checked it out) once exceeded — it does not close anything, only reports. `connection-timeout` is a per-*caller* "how long will I wait for any connection" clock. Set `leak-detection-threshold` (2s) *shorter* than `connection-timeout` (5s), and a leak gets logged, by name and stack trace, up to 3 seconds *before* the first caller-facing failure — an operator watching logs (or an alert on that WARN) finds out about the leak before any user does. Set it the other way around (longer than `connection-timeout`, or left disabled, as it was during this incident), and the first signal anyone sees is a caller-facing 500, with no indication of which code opened the connection that caused it — exactly what happened here. 2 seconds itself is chosen the same way as `connection-timeout` above: nothing in this codebase's own measured behavior ever holds a connection anywhere near that long, so it will not false-positive on legitimate work.

**What a bounded pool does and does not do, stated explicitly:** none of the three settings above caused this incident, and none of them would have prevented it. A connection that is never closed is gone from the pool's usable capacity regardless of how big the pool is, how long a caller is willing to wait for one, or how quickly a leak gets logged — the only thing that stops the *leak* is the code fix above. What these three settings change is how *visible* and how *contained* the same defect would have been: a smaller pool exhausts (and therefore surfaces) sooner; a shorter timeout makes each individual failure cheaper and faster to observe; `leak-detection-threshold` gives an operator a named, stack-traced warning before users are affected at all. They bound blast radius and shorten detection time. They are not the fix.

**Postgres-side timeouts**, added per-session via Hikari's `connection-init-sql` (executed once per newly-established physical connection, in both `application.yml` and, merged with the existing timezone pin, `application-test.yml`):

```
SET statement_timeout = 5000; SET idle_in_transaction_session_timeout = 60000;
```

Chosen **per-session over the alternatives, deliberately**: container-level config (a custom `postgresql.conf` baked into the `wmp-db` service in `docker-compose.yml`) would only ever apply to that one dev container — it would not reach the Testcontainers-spawned Postgres the integration test suite runs against (each of those starts its own fresh `postgres:16-alpine` container from the base image, with no custom config layered in), and it would have no effect at all on any other Postgres instance this application might connect to, including an unrelated native Postgres 18 install this machine happens to also have on the standard port 5432 — that instance is not part of this project's compose file or connection string at all, and container config could never reach it regardless. A per-role setting (`ALTER ROLE wmp SET ...`) would need to be applied as a one-time manual DDL step against every environment's database, another thing that would silently not exist against a fresh Testcontainers instance unless separately scripted. Setting both via `connection-init-sql` means every physical connection this application ever opens, against any Postgres instance, in dev or in the test suite, carries both settings from the moment it's created — no separate per-environment setup step to forget.

- **`statement_timeout = 5000`** — the slowest real query observed anywhere in this project's own measurements (`docs/measurements.md`, the unindexed offset-pagination baseline) was still under 40ms. 5 seconds is well over 100x that observed worst case, generous enough to never interrupt legitimate work, while still bounding a genuinely runaway or lock-blocked query to a finite, bounded wait instead of an indefinite one.
- **`idle_in_transaction_session_timeout = 60000`** (60s) — added honestly, not because it addresses this incident. **It would not have caught this one**: §4 already established that every leaked connection here showed as plain `idle`, never `idle in transaction`, because the leaked statements ran to completion (autocommit) rather than leaving an open transaction behind. This setting exists for a *different* failure mode this codebase could still introduce: application code that opens an explicit transaction (a `@Transactional` method, or any multi-statement unit of work) and then stalls, hangs, or throws in a way that never reaches `commit()` or `rollback()` — a genuinely stuck transaction, as opposed to this incident's genuinely-finished-but-never-returned connection. 60 seconds is chosen the same way as the other thresholds: no legitimate transaction in this codebase (all short, request-scoped `@Transactional` service methods, no user-interaction-in-the-middle patterns) should ever need anywhere near that long, so this bounds a real class of future bug without risk of cutting off real work.

**Regression test.** `PayrollAccrualJobLeakIT` (new) asserts directly on `HikariPoolMXBean.getActiveConnections()` after calling `PayrollAccrualJob.run()` synchronously — no HTTP layer, no sleep, no timeout-and-hope: by the time a synchronous call returns, every connection it was ever going to open has either been returned (fixed) or is still checked out (broken), so the assertion is immediate and deterministic. It runs under its own `@ActiveProfiles("leak-test")` context (`application-leak-test.yml`, `maximum-pool-size: 3`) — the same singleton Testcontainers Postgres every other IT shares (`AbstractIntegrationTest`), just its own separate Hikari pool, so a fully-exhausted 3-connection pool here cannot affect any other IT class. The fixture creates 15 `ACTIVE` employees itself; at the (now-removed) 1-in-5 leak rate that would have leaked exactly 3 connections — this pool's entire capacity — guaranteeing deterministic exhaustion regardless of what other IT classes' own fixtures also contribute as `ACTIVE` employees against the same shared database (more active employees elsewhere only means more leaks on the broken version, never fewer, and never breaks this test's own assertion either way).

**Verified both ways, not just written and trusted:**

- Against the leaky version (temporarily restored from commit `1e5c659`, the last leaky commit cited at the top of this document): **`BUILD FAILURE`**, `Tests run: 1, Failures: 1`, `expected: 0 but was: 3` — exactly the 3 connections the math above predicts, on the specific assertion this test exists to make.
- Fix restored, recompiled, re-run: `BUILD SUCCESS`, `Tests run: 1, Failures: 0`.

A regression test never seen failing is not a regression test; this one was seen failing, for the right reason, with the right number, before being trusted.

**`POST /actuator/payroll-accrual` stays.** It remains legitimate ops tooling — an on-demand trigger for a job that otherwise only runs at 2 AM, useful for exactly the same reason it was useful before (an operator wanting to run it now rather than wait for the cron window), and it is also what this regression test's sibling reasoning is built on (though the test itself calls `PayrollAccrualJob.run()` directly, not through this endpoint, precisely to avoid HTTP-layer noise in the assertion). The only thing that made it dangerous — the job it triggers leaking connections — is fixed. Removing it now would discard real operational value for no remaining safety benefit. It is still off the domain API surface entirely (Phase 8 Task 1a, `/actuator/payroll-accrual`, not `/api/v1/**`), so `OpenApiIT`'s "exactly 30 domain endpoints" assertion and `PermissionRegistry` are both unaffected by this decision either way.

## Prevention

These are two different claims, kept separate on purpose:

**What stops this exact defect from recurring:** the try-with-resources fix itself, and `PayrollAccrualJobLeakIT` guarding against its reintroduction — a future edit that removes the try-with-resources (or adds a new code path that similarly skips it) fails this test immediately, the same way it was just proven to fail against the original leaky commit. This is the only thing on this list that actually prevents a recurrence of *this specific bug*; everything else below only affects how fast a *future, different* leak would be noticed.

**What would have shortened time-to-detection, had this one still happened:** `leak-detection-threshold` (now enabled, 2s) would have logged a named, stack-traced `WARN` for the very first leaked connection, up to 3 seconds before any caller-facing failure — instead of the first signal anyone had being a submit-endpoint 500 with no indication of a batch job anywhere nearby. Separately, Phase 7's Grafana dashboard (`observability/grafana/dashboards/wmp-overview.json`) already plots `hikaricp.connections.active/.idle/.pending` over time; nothing about this incident required new panels to be visible in it (the evidence samples in `payroll-500s-evidence.md` show exactly the `active=10, idle=0` signature that panel would have rendered) — what's still missing is an actual *alert* wired to that data (e.g., paging on `hikaricp.connections.pending > 0` sustained for some window), which would turn "visible if someone happens to be looking at the dashboard" into "someone gets paged." That alerting is not implemented as part of this task — noting it as a real gap rather than treating the existing dashboard as sufficient on its own.
